# Paying Subscribers — SkyWall

A WordPress plugin for the existing SkyWall app login. Stripe hosts checkout and runs billing. This site maps a SkyWall subscription to a **local WordPress user**, sends new users the standard set-password email, and grants the existing `paying-subscriber` role. It does not send passwords, change an existing user's password, or create a WooCommerce order. WooCommerce remains the source of installer files; its paid Subscriptions extension is not required for direct Stripe checkout. The legacy Woo subscription hook is retained.

## Start on an isolated staging site

1. Back up the site and database. Staging must have a separate user database, no live payment credentials and a mail catcher (or a controlled test inbox). Do not connect Stripe test events to the production user database. Use normal WordPress staging/local environment detection. If the host labels a genuinely isolated sandbox as production, a developer may set `SKYWALL_ALLOW_TEST_WEBHOOKS` to boolean `true` **on that staging installation only**.
2. Build with `python3 tools/package.py paying-subscribers.zip`. The default ZIP folder is `paying-subscribers-master`, matching the existing SkyWall plugin basename. Upload as a **replacement** for the existing plugin, not a second active copy. On a fresh site install and activate normally. No Stripe webhook is operational until configured.
3. In **Settings → SkyWall billing**, select Sandbox. Set the **Payment Link ID** (`plink_…`, not the public `buy.stripe.com` URL), **monthly price ID** (`price_…`, not a product ID), and target **Woo product ID** (default `45`; staging IDs may differ). Configure a sandbox **restricted Stripe API key** with read access to subscriptions and invoices. No charge, checkout, refund or subscription-write API access is needed. Use sandbox and live credentials from their respective environments. Treat these keys as secrets; do not send them in chat.
4. In Stripe's sandbox **Workbench → Webhooks**, create a snapshot event destination for **your account** using the HTTPS endpoint displayed by the plugin (`/wp-json/skywall/v1/stripe-webhook`). Select `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `invoice.paid`, `invoice.payment_failed`, `customer.subscription.updated`, `customer.subscription.deleted`. Copy that destination's signing secret (`whsec_…`) into SkyWall billing. Never use the Stripe CLI signing secret for a Dashboard endpoint. Save the settings. The customer-facing success URL is *not* this endpoint; direct buyers to instructions to check their email and visit **My Account**.
5. The admin UI keeps keys in WordPress options (not autoloaded), masked on subsequent visits; secure the database and backups. If your host supports managed configuration, define `SKYWALL_STRIPE_MODE`, `SKYWALL_STRIPE_LINK_ID`, `SKYWALL_STRIPE_PRICE_ID`, `SKYWALL_STRIPE_API_KEY`, `SKYWALL_STRIPE_SECRET` and/or `SKYWALL_STRIPE_PRODUCT_ID` instead. Constants override the corresponding UI values. Mode is `test`, `live`, or empty (off). Never commit keys. Turning off the webhook does **not** cancel a subscription in Stripe or reverse access already granted.

## Acceptance before changing the public buy button

- Store the installer in a Woo-approved **local, protected `uploads/woocommerce_uploads/` directory** and attach it to the staged product. Ordinary public media URLs, remote/cloud/CDN-only files, symlinks and paths outside this directory are not served. Check that the actual raw file URL **denies anonymous downloads** at the origin and any CDN. Only then check **Settings → SkyWall billing → Installer downloads**. This attests to protection; it does not configure it. The equivalent configuration constant is `SKYWALL_WOO_DOWNLOADS_PROTECTED` (boolean). If the host cannot protect the file, leave delivery disabled. For a page outside Woo My Account use `[skywall_downloads]`.
- Use the sandbox Payment Link **as a brand new customer**, not a WordPress administrator. Confirm `$15/month`, pay with Stripe's test method, check an active subscription and next invoice date in Stripe. Verify successful webhook deliveries in Workbench.
- Open the password setup email at the **buyer's** address. Set a password, sign in, open My Account, download the installer and confirm its expected version/checksum. Verify the same ordinary account is recognized by the SkyWall app. For a first purchase using an existing WordPress account, sign in to that account and confirm the subscription in My Account; its password and unrelated roles stay unchanged. Later renewals use the saved Stripe IDs, not the current checkout email.
- Resend the checkout event: no duplicate account or welcome email. Exercise a renewal and a cancellation: even an immediate cancellation keeps the already established paid-through date, never a new term. Once that time elapses, the local download check expires immediately and WP-Cron removes the app role. Keep scheduled jobs running. A failed or pending renewal does not extend the paid period. A missing installer or undelivered email is a fulfillment error; billing alone does not prove delivery. Use WordPress's normal lost-password flow to recover an undelivered onboarding email.
- Only after those checks, repeat configuration with the **live** IDs, a separate live destination and its live signing secret on production. Point the public button to the **live** Payment Link only when ready. Do not reuse sandbox bindings, restore staging users to production, or send test charges to live.

## Running local checks

Use `php tests/transport.php`, `php tests/access.php`, `php tests/claim.php`, and `php tests/downloads.php` for deterministic component checks. `tests/wp-integration.php` additionally exercises the plugin behind the actual WordPress REST dispatcher with WooCommerce installed; it intercepts Stripe HTTP and email, **not** WordPress users, roles or database writes. This test requires a fresh disposable local WordPress installation at `http://skywall.test`, `WP_ENVIRONMENT_TYPE=local`, WooCommerce and this plugin active. Run `SKYWALL_DISPOSABLE_TEST_DB=1 wp eval-file tests/wp-integration.php` only in that fixture. It writes test users, product files and fixture settings there. Never use the test harness on a real site.
