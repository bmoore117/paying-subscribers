# Stripe subscriber access implementation plan

> For Hermes: use subagent-driven-development for independent components and review.

**Goal:** Turn a paid SkyWall Stripe Payment Link subscription into a WordPress login, the existing `paying-subscriber` role and access to the SkyWall installer; no production changes.

**Architecture:** A signed WordPress REST endpoint accepts only the configured mode/offer. Use verified checkout to establish the subscription-to-user mapping and fetch current Stripe subscription state when projecting billing events. Only a paid SkyWall subscription can start access; preserve unrelated user roles. WordPress owns user creation and set-password email. The existing Woo downloadable product owns the installer files.

**Tech stack:** PHP, WordPress REST and user APIs, Stripe v1 snapshot events and read-only API, WooCommerce product downloads.

1. `includes/stripe.php`: webhook signature, route, credential/mode checks and Stripe API lookup; tests in `tests/transport.php`. No HTTP call to Stripe before signature/offer validation.
2. `includes/access.php`: map checkout to WP user and update paid roles using authoritative current subscription status; handle replay and event order; tests in `tests/access.php`. On retries don't reset passwords or mail twice.
3. `includes/downloads.php`: serve product 45 downloads only after a logged-in user is entitled, with links in My Account. Use WooCommerce delivery mechanisms where possible. Test ordinary, denied and missing-file paths.
4. `paying-subscribers.php`/`README.md`: wire modules, document safe sandbox setup, keep registration and hosting independent of Hermes; do not replace other roles. Exercise plugin in a disposable WordPress environment if available, review, and package a clean ZIP.
